# Технические требования

[← Алгоритм планирования](02_algoritm_planirovaniya.md) · [Интерфейс и анимации →](04_interfeis_i_animacii.md)

## 1. Общая архитектура

Приложение состоит из независимо заменяемого браузерного интерфейса и серверной
части. Они обмениваются только через версионированный программный интерфейс
(API — формальный набор сетевых запросов и ответов). Браузер не обращается к
SQLite напрямую и не содержит окончательных правил расчёта сроков, состояний или
планирования.

Сервер реализуется на Python с FastAPI. FastAPI отвечает за сетевой слой,
проверку формы запросов, документацию API и преобразование ошибок, но не хранит
предметные правила внутри обработчиков запросов.

Рекомендуемая схема зависимостей:

```text
Браузерный интерфейс / будущий Telegram-бот / будущий агент
                         ↓
            Версионированный HTTP API
                         ↓
          Прикладные сценарии приложения
                         ↓
      Предметная модель и чистый планировщик
                         ↓
 Хранилище SQLite / часы / уведомления / внешние адаптеры
```

Зависимости направлены внутрь: предметная модель не импортирует FastAPI,
библиотеку базы данных, код интерфейса, Telegram или Codex CLI.

## 2. Слои серверной части

### 2.1. Предметная область

Содержит сущности, типы значений, состояния, правила переходов и алгоритм
планирования. Этот слой:

- работает с обычными объектами Python;
- получает текущее время через переданный интерфейс часов;
- не выполняет сетевые запросы;
- не открывает соединение с базой;
- не знает формат HTTP-ответов;
- выдаёт структурированные решения и ошибки предметной области.

Основные модули: задачи, группы и ярлыки, календарь и вместимость, планирование,
рабочие сессии, сроки и уведомляемые события, отчёты.

### 2.2. Прикладной слой

Описывает законченные действия пользователя: создать задачу, изменить рабочий
интервал, получить неделю, построить предварительный план, подтвердить его,
запустить таймер, завершить задачу, собрать отчёт.

Каждый сценарий:

- принимает отдельную входную модель;
- загружает нужные данные через абстракции хранилища;
- вызывает предметные правила;
- сохраняет изменения в одной транзакции;
- публикует предметные события после успешной записи;
- возвращает модель результата, не связанную с таблицами SQLite.

Чтение недельного экрана может использовать отдельный оптимизированный запрос,
но результат должен иметь тот же смысл, что предметные сущности.

### 2.3. Сетевой слой

Содержит маршруты FastAPI, входные и выходные схемы Pydantic (библиотеки
проверки структурированных данных), преобразование ошибок и зависимости
запроса. Обработчики должны быть короткими: проверить доступ, вызвать один
прикладной сценарий и вернуть результат.

Запрещено:

- выполнять запросы SQL непосредственно в маршрутах;
- дублировать формулу вместимости на уровне API;
- возвращать внутренние объекты базы как сетевой договор;
- смешивать генерацию HTML с предметной логикой.

### 2.4. Инфраструктурный слой

Содержит SQLAlchemy 2 (библиотеку сопоставления объектов и таблиц), реализации
хранилищ, транзакции, миграции Alembic (последовательные изменения структуры
базы), системные часы, журналирование, резервное копирование и будущие внешние
адаптеры.

Заменяемые интерфейсы требуются как минимум для:

- хранилищ задач, календаря, сессий и уведомлений;
- единой транзакции прикладного сценария;
- часов и часового пояса;
- отправки уведомлений;
- постановки внешней работы в очередь;
- генерации идентификаторов.

## 3. Рекомендуемая структура исходников

Конкретные названия можно уточнить, но границы должны сохраниться:

```text
backend/
  app/
    domain/          # сущности, правила, события, планировщик
    application/     # команды, запросы, модели результата, порты
    infrastructure/  # SQLite, хранилища, часы, внешние адаптеры
    api/              # FastAPI, маршруты, сетевые схемы
    bootstrap/        # сборка зависимостей и настройки
  migrations/
  tests/
frontend/
  src/
    features/        # законченные пользовательские возможности
    entities/        # отображаемые модели и компоненты сущностей
    shared/          # сетевой клиент, базовые элементы, стили
  tests/
```

Сетевые типы интерфейса желательно генерировать из схемы OpenAPI —
автоматического описания запросов FastAPI. Это уменьшит расхождения, но
сгенерированный код не должен становиться источником бизнес-правил.

## 4. Браузерный интерфейс

Интерфейс рекомендуется реализовать как отдельное приложение на TypeScript
(JavaScript с проверкой типов) и компонентной библиотеке, например React.
Окончательный выбор библиотеки не влияет на договор сервера.

На первом этапе собранные статические файлы может раздавать тот же локальный
сервер, но разработка и тестирование интерфейса остаются отдельными. Все запросы
идут по пути `/api/v1`.

Для недельной сетки в первой версии рекомендуется обычная разметка браузера:
CSS Grid (табличная сетка средствами стилей) и позиционируемые поверх неё блоки.
Семь дней по 96 пятнадцатиминутных ячеек — небольшой объём, не требующий Canvas
(программно рисуемого полотна). Обычная разметка проще для клавиатуры,
доступности, текста, подсказок и автоматических тестов.

Отрисовку сетки следует скрыть за отдельным компонентным договором. Если позднее
появится просмотр большого диапазона или измеренная проблема скорости,
внутреннюю реализацию можно заменить на Canvas без изменения серверного API.

## 5. Хранилище SQLite

### 5.1. Общие правила

SQLite является основной базой первой версии. Требуется:

- включить проверку внешних ключей для каждого соединения;
- использовать режим журнала WAL — запись изменений в отдельный журнал для
  более устойчивого одновременного чтения и записи;
- задать ограниченное ожидание занятой базы вместо мгновенного падения;
- держать транзакции короткими;
- выполнять пакетное применение плана одной транзакцией;
- использовать миграции с первого изменения схемы;
- не запускать несколько серверных процессов, одновременно пишущих в один файл,
  без отдельной проверки режима эксплуатации.

Для локальной однопользовательской версии рекомендуется один серверный процесс.
Переход к многопользовательскому размещению потребует серверной базы, например
PostgreSQL, но не должен потребовать переписывания предметной области.

### 5.2. Идентификаторы и версии

Сущности получают UUID — случайные строковые идентификаторы, не зависящие от
номера строки SQLite. Изменяемые основные записи имеют поля `created_at`,
`updated_at` и целочисленную `version`.

Версия нужна для оптимистической блокировки: если два действия меняли одну
запись, второе не перезаписывает первое молча, а получает конфликт версии.

### 5.3. Время и длительность

- Моменты времени сохраняются в UTC — единой мировой шкале, а при выводе
  переводятся в часовой пояс рабочей области.
- Локальная календарная дата хранится отдельно там, где смысл привязан к дню,
  например у рабочих интервалов и отчётов.
- Длительность хранится целым числом секунд; плановые оценки дополнительно
  проверяются на кратность шага сетки при размещении.
- Значение времени окончания всегда строго больше начала.
- Неделя вычисляется в часовом поясе рабочей области, а не сервера.

## 6. Минимальная схема данных

Имена ниже являются смысловым договором; окончательные названия столбцов можно
уточнять миграциями.

### 6.1. Настройки и классификация

- `workspaces`: название, часовой пояс, начало недели, шаг сетки, видимые часы,
  настройки планировщика и версия.
- `group_types`: системные и пользовательские типы групп.
- `groups`: рабочая область, тип, название, описание, цвет, необязательный
  период или общий срок, значения по умолчанию, состояние.
- `labels`: рабочая область, необязательная группа, название, цвет, порядок,
  состояние.

### 6.2. Задачи и будущие цели

- `tasks`: рабочая область, необязательная группа, название, описание,
  состояние, срок, ранний старт, вес важности, оценка и оставшаяся длительность,
  правила деления, переопределение цвета, даты жизненного цикла, версия.
- `task_labels`: связь многих задач со многими ярлыками и признак основного
  ярлыка.
- `goals`: зарезервированная расширяемая сущность с названием, сроком,
  важностью и состоянием; полноценное использование включается после уточнения
  требований.
- `goal_tasks`: связь целей и задач без предположения, что задача принадлежит
  только одной цели.

### 6.3. Календарь

- `availability_intervals`: дата, локальное начало и окончание, источник
  (ручной или шаблон), версия.
- `availability_templates`: необязательные недельные шаблоны и период действия.
- `fixed_event_rules`: разовое или еженедельное событие, период, локальное время,
  дни недели, название, необязательная группа, состояние.
- `fixed_event_exceptions`: отмена или изменение отдельного экземпляра правила.
- `schedule_blocks`: задача, начало, окончание, источник, состояние,
  закрепление, признак принятого риска, версия и необязательный запуск
  планировщика.
- `schedule_conflicts`: блок, вид конфликта, пересекаемая сущность, длительность,
  состояние решения и момент подтверждения риска.

Повторяющиеся события хранятся как правило и исключения, а не заранее созданные
строки на годы вперёд. Недельный запрос разворачивает только нужный диапазон.

### 6.4. Фактическое время и отчёты

- `work_sessions`: необязательная задача и группа, состояние, способ создания,
  заметка, итоговая чистая длительность, версия.
- `work_session_segments`: отрезки работы между запуском/продолжением и
  паузой/завершением. У активной сессии последний отрезок не имеет окончания.
- `daily_reports`: локальная дата, момент сборки, итоговые числа, снимок списков,
  заметка и признак устаревания.

Ограничение базы и прикладной сценарий должны обеспечивать не более одной
активной рабочей сессии на рабочую область.

### 6.5. Планировщик, уведомления и история

- `planner_runs`: входные параметры, версия исходного календаря, состояние
  предварительного результата, итог и время жизни.
- `planner_run_items`: решения и причины по задачам и блокам; допускается
  структурированное поле JSON при наличии проверяемой версии формата.
- `notifications`: тип, важность, связанная сущность, текстовые параметры,
  состояние и моменты прочтения, откладывания и решения.
- `outbox_events`: события, ожидающие передачи будущим внешним каналам;
  записываются в той же транзакции, что основное изменение.
- `audit_log`: важные пользовательские действия до и после изменения без
  хранения секретов и избыточного содержимого заметок.

## 7. Программный интерфейс версии 1

Все пути начинаются с `/api/v1`. Формат обмена — JSON. Даты и моменты времени
передаются в стандартизованном строковом виде с часовым поясом.

### 7.1. Недельное представление

- `GET /week?start=YYYY-MM-DD` — один согласованный снимок недели: дни,
  вместимость, рабочие интервалы, события, блоки, конфликты и сводные числа.
- `GET /capacity?from=...&to=...` — вместимость диапазона для карточек и
  предварительных проверок.

Ответ недели должен быть готов для отображения, но не содержать вычислений,
которые интерфейс обязан повторять для проверки истинности.

### 7.2. Справочники и задачи

- стандартные операции создания, чтения, изменения и архивации для `/groups`,
  `/labels`, `/tasks`;
- `GET /tasks` с фильтрами, сортировкой и постраничной выдачей;
- `POST /tasks/{id}/complete`, `/cancel`, `/archive`, `/restore` — явные переходы
  состояния вместо произвольной записи поля;
- административное удаление вынесено в `/admin/tasks/{id}` и требует отдельного
  подтверждающего параметра.

### 7.3. Календарь

- операции над `/availability-intervals` и `/availability-templates`;
- операции над `/fixed-events` и их исключениями;
- операции создания и изменения `/schedule-blocks`;
- отдельные действия закрепления и снятия закрепления блока.

### 7.4. Автоматическое планирование

- `POST /planner/previews` — создать предварительный результат;
- `GET /planner/previews/{id}` — получить объяснения и блоки;
- `POST /planner/previews/{id}/apply` — подтвердить весь результат или выбранные
  элементы;
- `DELETE /planner/previews/{id}` — отменить неиспользованный вариант.

Применение требует версию исходных данных и уникальный ключ повторного запроса,
чтобы двойное нажатие не создало дубликаты.

### 7.5. Таймер и отчёты

- `GET /timer/active` — восстановить состояние рабочего режима;
- `POST /work-sessions/start`, `/{id}/pause`, `/{id}/resume`, `/{id}/finish`;
- `POST /work-sessions/manual` — ручная запись;
- `GET /reports/daily/{date}` и `POST /reports/daily/{date}/compile`.

Браузер отображает секунды локально от серверной отметки начала, но после каждого
действия сверяется с сервером. Сервер является источником истины.

### 7.6. Уведомления

- `GET /notifications` с фильтрами;
- действия прочитать, отложить и решить;
- отдельный запрос количества новых уведомлений для верхней панели.

## 8. Договор запросов и ошибок

Каждый изменяющий запрос проверяет версию сущности. Успешный ответ возвращает
новую версию и актуальные вычисляемые состояния.

Единый ответ об ошибке содержит:

- постоянный машинный код;
- понятное русское сообщение;
- необязательный путь ошибочного поля;
- сведения для разрешения конфликта;
- идентификатор запроса для журнала.

Отдельные коды требуются для неверного интервала, конфликта версии, активного
таймера, устаревшего предварительного плана, запрещённого пересечения,
недостаточной вместимости и недопустимого перехода состояния.

## 9. События и будущие интеграции

После значимых изменений прикладной слой создаёт события: задача создана,
изменена, просрочена или выполнена; блок размещён или конфликтует; таймер начат
или завершён; дневной отчёт собран.

Сейчас события используются для внутренних уведомлений и журнала. В будущем
таблица исходящих событий позволит отправлять их в Telegram без изменения
сценариев задач.

### 9.1. Telegram-бот

Будущий бот вызывает те же прикладные сценарии через отдельный адаптер или API.
Он не пишет в SQLite напрямую. Потребуются привязка пользователя, проверка прав,
защита повторных команд и отображение времени в часовом поясе рабочей области.

### 9.2. Программный агент

Будущий агент не получает прямой доступ к базе и не запускается внутри
обработчика HTTP-запроса. Его работа оформляется как отдельное задание с
ограниченным входом и выходом.

Предполагаемые полезные сценарии:

- разбор текста пользователя в предварительные задачи;
- объяснение перегруженной недели;
- предложение декомпозиции крупной задачи;
- черновик дневного или недельного отчёта;
- предложение изменений плана.

Любое изменение агента сначала является предложением и требует подтверждения.
Команды операционной системы выполняются только по разрешённому списку, с
ограничением времени, отдельным рабочим каталогом, журналом и возможностью
отмены. Секреты и весь файл базы агенту не передаются.

## 10. Надёжность и восстановление

- Все изменения схемы выполняются миграциями и проверяются на копии базы.
- Приложение предлагает создать резервную копию SQLite из административного
  раздела штатным механизмом базы, а не простым копированием во время записи.
- Должна быть выгрузка основных данных в человекочитаемый JSON и, желательно,
  таблицы CSV.
- При аварийном завершении активная сессия восстанавливается; пользователь может
  исправить её окончание вручную.
- Предварительные планы имеют ограниченный срок жизни и очищаются отдельно от
  подтверждённых данных.
- Операции удаления показывают последствия и ведут журнал.

## 11. Безопасность первой версии

По умолчанию локальный сервер слушает только `127.0.0.1`, то есть доступен с
этого компьютера. Открытие доступа в сеть требует явной настройки и механизма
входа.

Обязательно:

- строгая проверка всех входных данных;
- ограниченный список источников запросов браузера;
- отсутствие SQL и командной строки, собранных из пользовательской строки;
- экранирование пользовательского текста при выводе;
- отсутствие секретов и полного текста личных заметок в журналах;
- защита административного удаления повторным подтверждением;
- отсутствие функций запуска агента до отдельного проектирования угроз.

## 12. Производительность

Основной недельный экран содержит не более 672 базовых ячеек времени, поэтому
его следует получать одним согласованным запросом без отдельного запроса на
каждую задачу или день.

Ориентиры для локального компьютера среднего класса на тестовой базе:

- открытие недели с 500 блоками — не более 500 мс на сервере;
- фильтрация 20 000 задач с постраничной выдачей — не более 500 мс;
- предварительное размещение 200 задач на горизонте 12 недель — не более 2 с;
- действия таймера — не более 300 мс без учёта отрисовки.

Это критерии измерения, а не повод преждевременно усложнять хранение. При
отклонении сначала измеряются запросы и алгоритм.

## 13. Проверки качества

### 13.1. Модульные проверки

Чистые проверки предметных правил должны покрывать:

- расчёт вместимости и вычитание пересечений;
- порядок задач по сроку, запасу и важности;
- деление и неделимость;
- дефицит 15, 30 и 45 минут;
- границы дня, недели и часового пояса;
- переходы состояний задачи и таймера;
- восстановление активной сессии.

### 13.2. Интеграционные проверки

На временной SQLite проверяются миграции, внешние ключи, транзакционность
пакетного плана, конфликт версий, повторное применение одного запроса и
разворачивание повторяющихся событий.

### 13.3. Проверки договора и интерфейса

Схема OpenAPI фиксируется как проверяемый договор. Сквозные браузерные сценарии
проверяют создание задачи, выделение рабочего времени, пакетный план, ручной
перенос, таймер, завершение и отчёт.

Особенно важно проверять инварианты случайно сгенерированными календарями:
обычный автоматический блок не пересекает занятое время, закреплённый блок не
двигается, а подтверждённый конфликт всегда имеет причину и отметку согласия.

## 14. Готовность серверной части

Серверный этап нельзя считать законченным, пока:

- все основные сценарии доступны без браузера через документированный API;
- предметный планировщик проверяется без FastAPI и SQLite;
- новая пустая база создаётся всеми миграциями;
- недельный снимок и пакетное применение транзакционны и защищены версиями;
- таймер переживает перезапуск;
- ошибки имеют постоянные коды;
- существует резервное копирование и восстановление на тестовой базе;
- будущие Telegram- и агентские адаптеры не требуют прямого доступа к таблицам.
