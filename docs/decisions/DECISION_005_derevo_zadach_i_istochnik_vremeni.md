# DEC_005 — Дерево задач и единый источник фактического времени

[← К журналу решений](index.md)

## Контекст

Планировщику нужны большие задачи с декомпозицией на проекты, спринты и
конкретные действия. Одновременно пользователь должен видеть не только итог
дня, но и интервалы работы над конкретной задачей. Отдельные сущности для
каждого уровня или дублирование времени в задаче создадут лишние источники
истины и риск двойного подсчёта.

## Решение

1. Каждая задача может ссылаться на родителя через `parent_task_id`; порядок
   соседей хранится в `child_position`.
2. Свойство `is_checkpoint` отдельно хранит намерение выполнять задачу как
   самостоятельную работу. Оно не меняет `parent_task_id` и может быть включено
   у промежуточного узла с потомками.
3. Календарь, автоплан, запуск и завершение используют конечные задачи и
   промежуточные узлы с `is_checkpoint = true`. Обычный узел с потомками
   остаётся организационной группой.
4. `WorkSession` и `WorkSessionSegment` остаются единственным источником
   фактического времени. API строит из них два представления: хронологию дня и
   группировку «задача → сессия → интервал».
5. Дневной отчёт обрезает каждый фактический интервал и каждый блок границами
   локальных суток. Клиент не должен повторно вычислять дневную выборку из
   полной истории сессий.
6. Пропуск срока является событием даты дедлайна. Он показывается в итогах этой
   даты и не переносится как новое предупреждение на следующие дни.
7. В общем списке задача остаётся плоской карточкой с подписью о родителе;
   дерево с отступами — это представление только страницы конкретной цели.
8. Архивирование цели не удаляет и не отвязывает дерево задач: связь и порядок
   сохраняются для восстановления. Окончательное удаление доступно только из
   архива; связанные блоки и история времени сохраняются как история.
9. Лист дерева является задачей. Узел с потомками является группой, а
   `is_checkpoint = true` у такой группы означает, что у неё есть ещё и
   собственная выполняемая работа. Это единая модель `Task`: вид в списке не
   изменяет ни положение в дереве, ни данные о сроке, сессиях и блоках.
10. Проект является развитием прежнего направления на тех же идентификаторах и
    внешних ключах. Новый программный интерфейс `/projects` существует рядом со
    старым `/directions`, пока слой совместимости нужен сохранённым клиентам.
11. Срочность проекта определяется ближайшим сроком активной выполняемой задачи:
    менее 24 часов — оранжевый сигнал, прошедший срок — красный с более высоким
    приоритетом.
12. Деревья цели и проекта используют те же карточки, что список задач.
    Глубина показывается отступом и соединительной линией, не меняя модель,
    порядок, сворачивание и действия узла.
13. Недельная нагрузка по дедлайнам и подсказки календаря строятся из того же
    серверного недельного снимка. Оставшаяся работа равна оценке минус минуты
    подтверждённых блоков, а доступное время ограничено текущим моментом и
    дедлайнами недели.
14. Сервер не принимает начало автоматического плана в прошлом: фактическая
    нижняя граница равна максимуму запрошенного начала и текущего момента.
15. Изменение времени конкретного блока не является переносом дедлайна задачи.
    Совмещённый редактор отправляет эти изменения раздельно; время блока можно
    указывать с точностью до минуты.

## Последствия

- Одна модель покрывает любое число уровней без новой таблицы «проектов» или
  «спринтов».
- Готовый узел не может случайно скрыть незавершённые пункты: обычная группа
  недоступна для завершения, а выполненный чекпоинт сохраняет дерево и может
  быть возвращён в активные.
- Новые клиенты, включая будущие Telegram-бот и агент, используют тот же API и
  не поддерживают собственный журнал времени.
- Для перемещения целого поддерева нужен будущий отдельный сценарий с явным
  подтверждением, а не массовое редактирование без проверки.
