# TASK_003 — Спроектировать системную архитектуру бэкенда

[← К дашборду](../../TASKS_DASHBOARD.md)

## Навигация

- [Журнал](./003_logs.md)
- [Выводы](./003_concl.md)

## Цель

Подготовить `BACKEND_DESIGN.md` — полное системное задание для реализации
серверной части планировщика: границы модулей и слоёв, модель данных SQLite,
прикладные сценарии, независимый от клиента программный интерфейс, транзакции,
события, надёжность, переносимые артефакты и этапы разработки.

## Границы

### Входит

- Структура серверного проекта и правила зависимостей между слоями.
- Переносимый каталог `artifacts/` для базы, копий, выгрузок, вложений, журналов
  и будущих запусков агента.
- Подробная реляционная модель данных, ограничения, индексы и политика удаления.
- Команды и запросы прикладного слоя для всего подтверждённого функционала.
- Версионированный HTTP API, не зависящий от браузера, Telegram или Codex CLI.
- Планировщик, таймер, уведомления, отчёты, журнал действий и исходящие события.
- Перенос, резервное копирование, восстановление, миграции и проверка качества.

### Не входит

- Написание программного кода и миграций.
- Проектирование конкретной реализации фронтенда.
- Реализация Telegram-бота или запуска программного агента.
- Развёртывание многопользовательского сервиса в интернете.

## Требования пользователя

- 2026-09-08 — не открывать и не использовать случайно присланную внешнюю ссылку.
- 2026-09-08 — создать файл системного дизайна бэкенда для следующего этапа
  реализации.
- 2026-09-08 — использовать SQLite и хранить базу и остальные изменяемые
  артефакты в отдельном аккуратно организованном каталоге проекта.
- 2026-09-08 — обеспечить перенос на другое устройство копированием или
  восстановлением папки артефактов.
- 2026-09-08 — спроектировать масштабируемую базу по всему ранее описанному
  функционалу.
- 2026-09-08 — сделать прикладную логику независимой от вызывающего клиента:
  фронтенда, Telegram-бота или скрипта Codex CLI.

Добавляйте сюда каждое существенное уточнение пользователя с датой.

## Критерии завершения

- [x] Создан и связан `BACKEND_DESIGN.md`.
- [x] Все бизнес-функции имеют прикладные сценарии и место в модели данных.
- [x] Для каждой основной таблицы описаны назначение, поля, связи и ограничения.
- [x] Определены каталог артефактов, переносимый снимок и восстановление.
- [x] API и прикладной слой не зависят от типа клиента.
- [x] Описаны транзакции, версии, повтор запросов, события и проверки.
- [x] Выводы, знания и архитектурные решения обновлены.
- [x] `python scripts/docs_ctl.py check` завершился без ошибок.

## План

1. Сопоставить бизнес-сущности с агрегатами, командами и запросами.
2. Спроектировать переносимое хранилище артефактов и жизненный цикл базы.
3. Описать слои, модули, схему SQLite и сетевой договор.
4. Проверить покрытие функций, целостность связей и сценарии отказа.
5. Обновить постоянную документацию и выполнить проверку.

## Допущения и ограничения

- Первая версия запускается локально для одного владельца, но все предметные
  записи сразу имеют `workspace_id`.
- FastAPI, SQLAlchemy 2, Alembic и SQLite являются выбранным стеком серверной
  части.
- Один процесс сервера пишет в один файл SQLite; многопользовательский режим
  позднее переводится на серверную базу через замены инфраструктурного слоя.
- Полноценные цели остаются расширением, но таблицы связей можно предусмотреть
  без включения пользовательского сценария.
- Копирование живой базы допустимо только при остановленном приложении;
  работающий сервер создаёт согласованный переносимый снимок штатным механизмом
  SQLite.

## Уточнения наследуемого контекста

- Если задача дочерняя, перечислите только уточнения и допустимые

## Рассмотренные варианты и обоснования

- Все клиенты должны вызывать одинаковые прикладные команды и запросы. FastAPI,
  Telegram и командная строка являются входными адаптерами, а не владельцами
  бизнес-логики.
- Живые артефакты не смешиваются с исходным кодом и не попадают в Git; каталог
  имеет стабильную внутреннюю структуру и манифест переносимости.
- Ключевые поля хранятся в обычных столбцах, JSON используется только для
  снимков, объяснений и неиндексируемых расширений.
- Просмотр недели и применение автоматического плана используют одну ревизию
  планирования, чтобы устаревший расчёт не записывался частично.
