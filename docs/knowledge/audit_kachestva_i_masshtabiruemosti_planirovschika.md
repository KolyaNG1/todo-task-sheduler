# Аудит качества и масштабируемости планировщика

[← К глобальным знаниям](index.md)

## Кратко

Текущий срез уже пригоден для демонстрации основного цикла «задача → рабочее
время → блок плана → таймер → завершение», но пока не является надёжной основой
для расширения. Главная причина — не объём функций, а отсутствие одного
авторитетного состояния: часть правил живёт в бэкенде, часть повторно вычисляется
во фронтенде, а некоторые производные признаки сохраняются в базе и устаревают.

Сначала необходимо исправить целостность данных, миграции и контракты. После
этого можно безопасно разделять крупные файлы и развивать интерфейс. Предлагаемый
порядок описан в [плане переработки](plan_refaktoringa_planirovschika.md), а
назначение конкретных файлов — в [карте кода](karta_koda_planirovschika.md).

## Метод и область проверки

- **Подтверждено:** просмотрены исходники бэкенда, фронтенда, миграций, запуска,
  тестов и документации требований в состоянии на 2026-09-10.
- **Подтверждено:** выполнены безопасные проверки через FastAPI TestClient и
  временные SQLite-базы; рабочая база пользователя не менялась.
- **Подтверждено:** восемь существующих тестов проходят; компиляция Python и
  проверка синтаксиса `frontend/app.js` проходят.
- **Ограничение:** клиентских автоматических тестов и измеренного покрытия нет;
  многопользовательская нагрузка и разные часовые пояса не проверялись.

Приоритеты: **P0** — риск неверных или непереносимых данных; **P1** — ломает
основной пользовательский сценарий; **P2** — мешает развитию или заметно
ухудшает работу; **P3** — локальный долг и удобство сопровождения.

## P0 — целостность и переносимость данных

### AUD-001 — цепочка миграций не запускается с нуля

- **Подтверждено экспериментом:** `alembic upgrade head` на пустой временной
  базе завершается `KeyError '0001_initial_schema'`.
- В `0001_initial_schema.py` фактический идентификатор равен `0001`, тогда как
  `0002_task_recurrence.py` ссылается на `0001_initial_schema`.
- Начальная миграция вызывает текущую `Base.metadata.create_all()`. Поэтому даже
  после исправления ссылки история останется неповторяемой: новый столбец из
  модели появится в миграции 0001, а следующая миграция попытается добавить его
  повторно.
- Запуск маскирует проблему: `bootstrap.py` использует `create_all()` и ручные
  `ALTER TABLE`, обходя Alembic.
- **Последствие:** нельзя доказуемо восстановить базу из истории схемы или
  безопасно обновлять её на другом устройстве.

### AUD-002 — временные метки сохраняются не в UTC

- `models.utcnow()` возвращает локальное время с поясом, а SQLite отдаёт его как
  значение без пояса. `stored_utc()` затем объявляет это значение временем UTC.
- **Подтверждено экспериментом:** на машине в `Europe/Moscow` разница после
  записи и повторного чтения составила `+10800` секунд.
- **Последствие:** дедлайны, уведомления, отчёты и сессии могут смещаться на три
  часа; перенос в другой пояс усугубит ошибку.

### AUD-003 — повторяющаяся задача не имеет экземпляров

- Единственный признак повторения — `Task.repeat_rule` со значениями `NONE` или
  `WEEKLY`; отдельного экземпляра задачи на дату нет.
- Завершение недельной задачи оставляет её `ACTIVE`, переносит дедлайн на семь
  дней и перезаписывает один `completed_at`, но старые подтверждённые блоки
  продолжают считаться её планом.
- **Подтверждено экспериментом:** после завершения и повторной загрузки задача
  остаётся `ACTIVE`, но имеет `PLANNED` и 60 запланированных минут. В дневном
  отчёте такое завершение даёт ноль выполненных задач.
- **Последствие:** следующий повтор нельзя корректно запланировать, история
  выполнений теряется, а блоки расписания нельзя независимо зачеркнуть.

## P1 — дефекты основных сценариев

| Код | Подтверждённый дефект | Последствие |
|---|---|---|
| AUD-004 | `create_block()` не проверяет остаток оценки и статус задачи. Временная проверка приняла второй полный блок уже полностью запланированной задачи с HTTP 201. | Одна задача размещается несколько раз; данные банка и календаря расходятся. |
| AUD-005 | После уменьшения доступного времени или добавления фиксированного события сохранённые `has_conflict` у блоков не пересчитываются. Проверка сохранила `[false, false]`. | Календарь скрывает реальные конфликты. |
| AUD-006 | `update_task()` возвращает модель без заранее загруженных блоков, а `task_view()` считает статус только по загруженной связи. Проверка вернула `UNPLANNED` для запланированной задачи. | Интерфейс временно показывает неверный статус после редактирования. |
| AUD-007 | Повтор уникального имени направления приводит к необработанному `IntegrityError` и HTTP 500. Аналогичный риск есть у тегов и профилей. | Обычная ошибка ввода выглядит как падение сервиса. |
| AUD-008 | Удаление задачи выполняется прямо в маршруте, а восстановление вызывает `get_task()`, который не возвращает записи с `deleted_at`. | Мягко удалённую задачу штатно восстановить нельзя. |
| AUD-009 | При переносе блока клиент считает мутацию подтверждённой, если сервер прислал тот же идентификатор, не сравнивая версию и время. | Старый ответ может вернуть блок назад или вызвать рывки других блоков. |
| AUD-010 | Для запросов недели нет номера поколения или отмены предыдущего запроса. | Быстрая навигация может отрисовать устаревшую неделю поверх новой. |
| AUD-011 | Завершение обычной задачи визуально завершает все её блоки, потому что состояние берётся у задачи, а не у конкретного блока/экземпляра. | Исторические и будущие размещения нельзя отразить независимо. |
| AUD-012 | Активный незакрытый отрезок сессии исключён из дневного отчёта. | Бар дня отстаёт от таймера до паузы или завершения. |
| AUD-013 | `start_session()` не запрещает запуск завершённой, отменённой или архивной задачи. | Жизненный цикл задачи нарушается. |
| AUD-014 | Интерфейс применяет только безопасные предложения автоплана; предложенный сервером конфликт нельзя явно принять или разрешить. | Сценарий «не хватает менее 30 минут — предупредить о нахлёсте» не завершён. |

## P1 — недостатки алгоритма планирования

- **AUD-015:** доступность до дедлайна считается целыми окнами, если начало окна
  раньше дедлайна, без обрезания конца по дедлайну. Срочность и объяснение могут
  быть ошибочными.
- **AUD-016:** `preferred_block_minutes` не влияет на нарезку. Проверка задачи на
  180 минут с предпочтением 60 минут создала один блок на 180 минут.
- **AUD-017:** начало горизонта не выравнивается по 15-минутной сетке. При
  `earliest_start_at=09:07` предложение началось в `09:07`.
- **AUD-018:** аварийный нахлёст строится от конца последнего исходного окна и
  может выйти за доступное время, горизонт или дедлайн без отдельной стратегии
  разрешения конфликта.
- **AUD-019:** статус планирования суммирует все подтверждённые блоки за всю
  историю, а не будущий объём текущего экземпляра и остаток работы.
- **AUD-020:** ручное размещение из банка использует предпочтительную длину или
  60 минут и способно частично разместить неделимую задачу.

## P1/P2 — границы бэкенда и контракты

- `PlannerService` размером около 45 КБ напрямую импортирует ORM-модели и
  SQLAlchemy и содержит почти все сценарии. Задуманные порты, хранилища и единая
  транзакция не реализованы.
- `router.py` содержит 37 маршрутов, вручную собирает ответы, напрямую работает
  с `Notification` и удалением `Task`, вызывает частный `_bump_revisions()`.
- Есть схемы входа, но нет типизированных схем ответа. Изменение словаря может
  незаметно сломать фронтенд, будущего бота или командный клиент.
- Поля канала, идентификатора запроса и ключа повторной отправки существуют в
  `RequestContext`, но HTTP-слой их не принимает и не использует.
- Версии строк почти нигде не проверяются. Только применение автоплана защищено
  `planning_revision`; параллельное редактирование задач и блоков перетирается.
- Нет проверки членства и прав рабочей области. Инициализация выбирает первую
  рабочую область и первого пользователя независимо друг от друга.
- `AuditLog` и `OutboxEvent` созданы в базе, но не заполняются. Поэтому нет
  доказуемой истории действий и надёжной очереди для будущего Telegram-бота.
- Список задач не имеет серверных фильтров, сортировки и постраничной выдачи.

## P1/P2 — модель предметной области

- У `ScheduleBlock` нет связи с запуском/предложением планировщика и нет
  состояний `COMPLETED`/`SKIPPED`; отмена — единственный жизненный переход блока.
- `Workspace.default_availability_profile_id` не имеет внешнего ключа.
- Даты исключений и фиксированных событий объявлены в Python как `datetime`,
  хотя столбец SQLite имеет тип `Date`.
- Статусы и виды в основном являются свободными строками без ограничений базы.
- Направление хранит `default_deadline_at`, но интерфейс и сервис его не
  принимают; отсутствуют описанные расширяемые поля и правила наследования.
- Архивное направление можно получить по идентификатору и назначить новой
  задаче.
- Теги не имеют порядка, версии и явного признака основного тега; в сообщениях
  сервиса осталось старое слово «ярлык».
- Нет отдельного остатка оценки, истории прогресса, связей задач с целями и
  произвольных расширяемых атрибутов.
- Фиксированное событие поддерживает один день недели или одну дату, но не
  исключения, несколько дней, редактирование одного экземпляра и период
  действия через интерфейс.
- Для доступного времени нет команды удалить исключение дня и вернуться к
  шаблону; сервер не требует кратность 15 минутам и не запрещает хранить
  пересекающиеся исходные строки.

## P1/P2 — состояние и устройство фронтенда

- Вся работа сосредоточена в одном `app.js` около 60 КБ и глобальном изменяемом
  объекте `state`; стили почти минифицированы в 14 физических строк. Это
  затрудняет поиск причин, рецензию и параллельные изменения.
- На каждое значимое действие часто перерисовываются весь банк задач и 21 день
  расписания через `innerHTML`. Теряются фокус, положение и локальная связь с
  перетаскиваемым элементом.
- Клиент повторно вычисляет `planned_minutes`, `planning_status`, сводный балл
  дня и объединение доступного времени. Эти правила уже есть или должны быть на
  сервере; расхождение породило несколько наблюдавшихся задержек отрисовки.
- `loadData()` одновременно запрашивает `/startup`, где задачи уже присутствуют,
  и `/tasks`. Один экран получает два снимка состояния.
- Фоновая сверка повторяется каждые 700 мс без предела попыток. Перемещённый за
  текущий 21-дневный горизонт блок никогда не подтвердится этим снимком.
- Константы 08:00–22:00, 15 минут и 21 день зашиты отдельно от настроек рабочей
  области. Ширина CSS также жёстко рассчитана на 21 колонку.
- Красная линия текущего времени обновляется только при полной отрисовке.
- Даты строятся смешением локального `Date`, UTC и
  `toLocaleDateString('sv-SE')`; возле полуночи возможен сдвиг дня.
- Нет ограничителя времени сетевого запроса, повторной попытки, проверки формы
  ответа и общего состояния «команда выполняется». Двойное нажатие может
  отправить повторную команду.
- Навигация не отражается в адресе: обновление страницы и кнопка «назад» теряют
  открытый раздел.
- Имя направления в карточке задачи вставляется без `escapeHtml()`. Это
  подтверждённая точка внедрения пользовательского HTML.
- Карточка выбирается мышью, но скрытый флажок и сама карточка не дают
  полноценной клавиатурной альтернативы. Доступность PR-25 не выполнена.
- Шрифты загружаются с Google Fonts; без сети запуск не полностью автономен и
  раскрывает внешний сетевой запрос.

## P2 — быстродействие и эксплуатация

- Представление 21 дня вызывает отдельные запросы доступности и фиксированных
  событий на каждый день — порядка 42 запросов до загрузки прочих сущностей.
- Применение плана и сериализация связей способны породить дополнительные
  ленивые запросы на задачу и направление.
- `/health` возвращает статический ответ и не проверяет доступ к базе, версию
  схемы и возможность записи в каталог артефактов.
- `planner.bat` удобен для локального старта, но не ждёт готовности процессов,
  не проверяет занятые порты и не имеет парной команды остановки. Повторный
  запуск может оставить конфликтующие процессы.
- Нет резервного копирования, восстановления и проверки переносимого снимка,
  хотя каталоги `backups/` и `exports/` зарезервированы.
- Статическая раздача не версионирует ресурсы; браузер может показывать старый
  JavaScript после обновления. Это соответствует повторявшимся жалобам на
  «исправление не появилось до перезагрузки».
- README бэкенда и фронтенда описывают целевое разделение как уже реализованное и
  потому вводят следующего разработчика в заблуждение.

| API | 3 интеграционных теста | Нет жизненного цикла задачи/блока, гонок, ошибок уникальности, восстановления, отчётов. |
| Миграции | Нет штатного теста | Свежая установка уже сломана. |
| Фронтенд | Нет автоматических тестов | Нет проверки мгновенной отрисовки, перетаскивания, завершения и навигационных гонок. |
| Сквозной сценарий | Ручная работа в браузере | Нет воспроизводимого теста «создать → разместить → перенести → завершить → перезагрузить». |

## Практические последствия

1. Не добавлять Telegram-бота или агента поверх текущего `PlannerService`: это
   закрепит неоднозначные контракты и размножит обходные пути.
2. Не начинать с косметического разбиения файлов. Сначала зафиксировать тестами
   инварианты времени, повторов, размещения и завершения.
3. Не выполнять одномоментное переписывание. Вводить новые модули за текущим
   `/api/v1`, переносить по одному сценарию и держать миграции обратимыми.
4. Перед любым переносом пользовательской папки сначала исправить и проверить
   цепочку схемы и UTC; существующей декларации «переносимо» недостаточно.
