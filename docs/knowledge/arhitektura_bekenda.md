# Архитектура бэкенда планировщика

[← К глобальным знаниям](index.md)

## Кратко

Полный системный проект находится в
[BACKEND_DESIGN.md](../../BACKEND_DESIGN.md). Бизнес-правила реализуются в
предметном и прикладном слоях. FastAPI, будущий Telegram-бот и Codex CLI являются
равноправными входными адаптерами и не обращаются к SQLite напрямую.

Изменяемые данные находятся в переносимом каталоге
[artifacts](../../artifacts/README.md). История проектирования — в
[TASK_003](../tasks/TASK_003_sproektirovat_sistemnuyu_arhitekturu_bekenda/003_descr.md).

## Состояние реализации

- **Подтверждено:** первый серверный срез находится в `backend/` и запускает
  FastAPI с версионированным префиксом `/api/v1`.
- **Подтверждено:** база создаётся из SQLAlchemy-моделей и начальной миграции
  Alembic; проверка миграции создала 22 таблицы, включая рабочие области,
  задачи, блоки расписания и рабочие сессии.
- **Подтверждено:** реализован сквозной сценарий: направление и ярлык → задача
  → доступное время и неподвижное событие → ручной блок → предварительный
  автоплан → подтверждение → запуск, пауза и завершение таймера.
- **Подтверждено:** HTTP-маршруты вызывают `PlannerService`; SQLAlchemy-модели
  не передаются через границу HTTP как бизнес-логика.
- **Подтверждено:** прикладной слой поддерживает изменение, завершение,
  отмену, архивирование и возврат задачи, перенос блока, ручные и таймерные
  сессии, а также вычисление дневного план/факта.
- **Подтверждено:** полностью размещённая задача не допускается к повторному
  автоплану на прикладном слое; при этом подтверждённый блок остаётся доступным
  для ручного переноса.
- **Подтверждено:** направления, теги и неподвижные события имеют операции
  изменения и архивирования; правило повторения задачи хранится отдельно от
  повторяющегося неподвижного расписания.
- **Подтверждено:** задача может быть родителем произвольного числа пунктов;
  её положение в дереве хранит `parent_task_id`, а возможность работать с ней
  как с чекпоинтом — отдельное поле `is_checkpoint`. В блоки и автоплан
  допускаются конечные задачи и явно отмеченные промежуточные чекпоинты.
- **Подтверждено:** задача с подтверждённым блоком не может стать обычным
  контейнером, пока блок не снят из плана. Явный промежуточный чекпоинт может
  иметь потомков и при этом учитывать собственную работу без потери дерева.
- **Подтверждено:** фактическое время не копируется в задачу: `WorkSession` и
  `WorkSessionSegment` остаются единственным источником, из которого сервер
  отдаёт хронологию и группировку по задачам.
- **Подтверждено:** дневной отчёт выбирает сессии по пересечению их отрезков с
  локальными сутками и обрезает отрезки границами дня. Поэтому длительность в
  «Работе по задачам», на временной шкале и в сумме «Факт» совпадает даже для
  сессии, пересекающей полночь.
- **Подтверждено:** отчёт отдаёт два согласованных ряда `actual_timeline` и
  `planned_timeline`; интерфейс рисует их рядом на одной шкале, не обращаясь к
  отдельному источнику истории.
- **Подтверждено:** завершение допустимой для выполнения задачи закрывает все
  открытые уведомления о её просрочке и не меняет `deadline_at`; повторное
  открытие возвращает её и завершённые блоки расписания в `ACTIVE` и
  `CONFIRMED` соответственно. Повторный возврат активной задачи с завершённым
  историческим блоком также безопасно возвращает блок в `CONFIRMED`.
- **Подтверждено:** архив является обратимым состоянием задач, целей,
  направлений, тегов и неподвижных событий. Архив задачи охватывает всё её
  поддерево; восстановление возвращает дерево и связи. Окончательное удаление
  разрешено только для записи, уже находящейся в архиве.
- **Подтверждено:** архив цели сохраняет её связь с задачами, их порядок,
  блоки и историю. Это заменяет устаревшее правило, по которому удаление цели
  отвязывало задачи.
- **Подтверждено:** команда изменения блока принимает явный признак переноса
  срока. При нём срок связанной задачи становится концом перенесённого блока,
  а открытые уведомления о просрочке этой задачи получают состояние
  `RESOLVED`. Уведомление о пропуске относится только к локальной дате срока:
  после смены дня открытая запись закрывается и не открывается повторно.
- **Подтверждено:** снимки дневных показателей сохраняются отдельно и доступны
  диапазоном дат; исходные интервалы при этом остаются источником подробностей.

## Подтверждённые сведения

- **Подтверждено:** схема покрывает все 15 бизнес-функций и 25 приёмочных
  сценариев.
- **Подтверждено:** предметный слой не зависит от FastAPI, SQLAlchemy, SQLite и
  типа клиента.
- **Подтверждено:** все предметные данные принадлежат рабочей области, имеют
  универсальные идентификаторы, версии и временные поля.
- **Подтверждено:** SQLite работает с одним серверным процессом, включёнными
  внешними ключами, журналом упреждающей записи и короткими транзакциями.
- **Подтверждено:** предварительный план защищён общей ревизией расписания и
  версиями задач, а применяется одной транзакцией.
- **Подтверждено:** таймер состоит из рабочей сессии и её отрезков; ограничения
  базы не допускают две незавершённые сессии в одной рабочей области.
- **Подтверждено:** API выдаёт подробности одной задачи вместе с её дочерними
  пунктами и сессиями, а также отдельную группировку всех сессий по задачам.
- **Подтверждено:** переносимый снимок создаётся штатным механизмом резервного
  копирования SQLite и сопровождается контрольными суммами.

## Решения

- **Решение:** хранить живую базу в `artifacts/database/planner.sqlite3`, а
  копии, выгрузки, вложения, журналы и будущие агентские запуски — в отдельных
  подпапках одного переносимого корня.
- **Подтверждено:** для Windows предусмотрен `Запустить планировщик.bat`: он
  использует уже установленный Python, запускает API на 8100 и статический
  интерфейс на 3000, не создаёт окружение и не устанавливает библиотеки. Порт
  5173 исключён, поскольку входит в зарезервированный Windows диапазон. Перед
  открытием страницы сценарий проверяет доступность обеих частей и не создаёт
  дубликаты уже работающих серверов.
- **Решение:** использовать единицу работы, оптимистичные версии, ключ повтора
  запроса и таблицу исходящих событий.
- **Решение:** поля, по которым выполняются поиск и фильтрация, хранить в обычных
  столбцах; JSON использовать только для снимков, объяснений и неиндексируемых
  дополнительных данных.
- **Решение:** сразу предусмотреть рабочие области, цели, внешние учётные записи
  и адаптеры, не публикуя неподтверждённые пользовательские сценарии.
- **Решение:** при добавлении поля повторения применять совместимое изменение
  SQLite при старте, чтобы локальные данные первой версии не требовали ручного
  переноса.
- **Решение:** использовать самоссылочную связь `tasks.parent_task_id` и
  `child_position` для проектов, спринтов и чекпоинтов вместо отдельной таблицы
  типов иерархии. Решение описано в
  [DEC_005](../decisions/DECISION_005_derevo_zadach_i_istochnik_vremeni.md).

Решение оформлено в
[DEC_003](../decisions/DECISION_003_bekend_i_artefakty.md).

## Гипотезы и непроверенные места

- **Гипотеза:** синхронная работа через SQLAlchemy и один процесс сервера будут
  самым простым и надёжным режимом для локальной первой версии.
- **Гипотеза:** обычного индексированного поиска SQLite хватит примерно до
  20 тысяч задач; полнотекстовый индекс следует добавлять только после замеров.
- **Гипотеза:** границы таблиц позволят перейти на PostgreSQL заменой
  инфраструктурных хранилищ без переписывания предметных правил.

## Практические последствия

- Новый клиент преобразует ввод только в уже существующие прикладные команды и
  запросы.
- Для переноса копируется остановленный каталог `artifacts/` либо согласованный
  снимок, но не отдельный файл работающей SQLite.
- Применение плана, завершение задачи с учётом времени и опасное удаление
  выполняются транзакционно.
- Фронтенд может получать типы из описания программного интерфейса и не знает о
  внутренних таблицах.
- Показ истории «по задачам» является представлением существующих сессий, а не
  второй системой учёта времени; это исключает расхождение отчёта и карточки
  задачи.
